# Архитектура Supabase

Рабочая архитектура: Android → Supabase Auth, Data API/RPC и Edge Functions → PostgreSQL.
Облачный проект last-paycheck Frankfurt Free (`mmuytwyhdwttzxuredfm`) развёрнут;
миграции 001–004 и Edge Functions `providers` и `catalog` применены. Ktor отсутствует в актуальном дереве;
историческая реализация сохранена коммитом ba1380c. Исходников Android в этой копии нет,
его подключение end-to-end ещё не проверено.

Реальные Auth, RLS двух игроков, приватные сохранения, административные CRUD и
исправление DELETE подтверждены HTTPS-проверками. Публикация тестового каталога
не выполнялась; demo-1 активен. Доказательства: [evidence](evidence/index.md).

## Разделение данных

- `lastpay`: исходные 13 таблиц каталогов и `user_save` для приватного снимка пользователя.
  Структура FK, UNIQUE, CHECK и индексов сохранена; Flyway не используется.
- `lastpay_private`: реестр администраторов, окна лимитов, аренды обновления кэша,
  справочник ISO и внутренние функции. В Data API эту схему не открывать.
- `lastpay_api`: 12 явных RPC и представление `user_save` с `security_invoker=true`.
  Только эта схема нужна новому клиенту в Exposed schemas.

`get_catalog`, `list_catalog`, `get_catalog_item` читают опубликованные данные
через функции SECURITY INVOKER и RLS. RPC нужны для прежних JSON-структур,
вложенных автомобилей/навыков, фильтрации, метаданных и серверного лимита.
Операции чтения RPC вызываются POST, поскольку обновляют счётчики лимитов.
Публичный браузерный GET в Edge Function `catalog` вызывает тот же `get_catalog`
с публичным ключом и возвращает только манифест опубликованной версии.

`list_draft_skills` и `get_draft_skill` также используют RLS и проверку реестра.
`create_draft`, `create_skill`, `update_skill`, `delete_skill`, `publish_catalog`
делегируют единственной проверяемой границе административной записи. Копирование,
блокировка ревизии, мутация и публикация выполняются одной SQL-транзакцией.

`save_game` сохраняет JSON-снимок только для `auth.uid()` с expectedRevision.
Это инфраструктура приватного сохранения, а не доверенная система игровой экономики
или проверка честности действий Android. Новая игровая функциональность не добавлялась.
`provider_cache` доступен только серверному `service_role` и используется Edge.

## Контракты

Полная таблица 24 операций: [operation-map.md](operation-map.md),
машиночитаемая версия: [operation-map.json](operation-map.json).
Ни одна исходная операция не удалена. У новых RPC один аргумент `args` типа JSONB.

Сохранены модели ресурсов, пагинация,
порядок списков, фильтры, ETag вида `"rev-N"`, If-Match как поле `args.ifMatch`,
неизменяемость публикаций, конфликты 409 и устаревшие ревизии 412. Передавать
If-Match нужно в JSON, а не в стандартном заголовке PostgREST.

Действующий контракт — [OpenAPI](../../openapi.yaml); доменные модели — server/supabase/contracts/catalog-models.yaml.
ER-источники — [Mermaid](../diagrams/backend-er.mmd) и [draw.io](../diagrams/backend-er.drawio).

Осознанные изменения транспорта:
- Старые пути `/api/v1/...` заменены RPC и `/functions/v1/providers/...`.
- Успешный delete_skill возвращает 200 с JSON receipt и сильным ETag после миграции 004.
- GET каталога становится POST RPC. Публичное чтение разрешено проектным публичным ключом.
- Операции, требующие секретных внешних API, теперь требуют сессию постоянного
  пользователя Supabase Auth; это защищает квоты от неавторизованных вызовов.
- Opaque admin token заменён пользовательским JWT и закрытым реестром администраторов.
- Location старого Ktor не выдаётся: новый RPC требует тело, а не переход по GET-ссылке.
- Ошибки домена имеют прежний `error.code/message/requestId/details`. Ошибки gateway,
  невалидный JWT, отсутствие GRANT EXECUTE, неверный JSON до входа в RPC,
  неизвестный RPC и неподдерживаемый HTTP-метод имеют штатный формат Supabase/PostgREST
  `code/message/details/hint`. Android должен нормализовать оба формата.
- Вызовы чтения могут получить 429. Для anon используется общий лимит 120/мин,
  для вошедших пользователей — по uid; IP-заголовкам клиента доверия нет.

Публикация собирает канонический JSON с сортировкой ключей и точными decimal,
вычисляет SHA-256 средствами PostgreSQL. Времена наблюдений нормализованы в UTC.
Новые DEMO-метаданные отличаются от Ktor, поэтому старый hash DEMO не переносится
как идентичный. Хэш новой публикации вычисляется по её собственному снимку.

## Провайдеры

Одна Edge Function `providers` обслуживает 5 маршрутов. Она верифицирует JWT
через серверный Auth `/auth/v1/user`, отвергает anonymous sessions и только затем
вызывает узкий сервисный RPC. Ключи не передаются Android. URL провайдеров заданы
в коде, редиректы не выполняются, ответ ограничен 2 МиБ, таймаут запроса — 10 с.

Проверяются параметры, структура, непустые данные, обрезанные страницы и эхо ключа.
401/403 → AUTH, 404 → NO_DATA, 429/5xx/редирект → UNAVAILABLE, таймаут → TIMEOUT.
Только TIMEOUT и UNAVAILABLE повторяются до 3 раз с паузами 1 и 2 с.
Ошибки не перезаписывают хороший кэш; истёкший кэш служит fallback с stale=true.
TTL World Bank — 30 дней, остальных — 7. Сырой JSON сохраняется как в исходном API;
нормализованы проверка структуры, ключи кэша и общий формат ответа.

Распределённая аренда обновления на 55 с защищает от повторных одновременных
обращений. Вторая проверка кэша после аренды закрывает гонку между чтением и захватом.
При занятой аренде возвращается stale-кэш либо 503. Неудачный запрос освобождает аренду;
при аварийном завершении она истекает сама. Сервисные операции недоступны клиентским JWT.

Лимиты интеграций: 30 запросов/мин на uid и 300/мин на весь проект.
Кэш ограничен 128 записями по максимум 2 МиБ, что ограничивает живые payload,
но не заменяет контроль общего размера БД и VACUUM. Нужны наблюдение за квотой
и периодическое обслуживание при большом обороте кэша. Платный Redis не требуется.
