# Безопасность Supabase

## Роли и доверие

Android получает только URL, публичный publishable/anon key и свою сессию Auth.
Публичный ключ идентифицирует проект, но не администратора. JWT подписывает и
проверяет Supabase; изменение user_metadata или app_metadata в клиентском запросе
не предоставляет роль администратора. Реестр `lastpay_private.admin_membership`
проверяет uid из верифицированной сессии. Клиент не имеет доступа к его изменению.
Администратора назначает владелец проекта вручную после создания подтверждённого пользователя.

Анонимный запрос может читать опубликованные каталоги. Обычный authenticated
пользователь не видит черновики. Supabase anonymous sign-in также не получает
приватное сохранение, право администратора или интеграции. Приватные сохранения
доступны только постоянному владельцу; администратор каталога не читает чужие сохранения.

`service_role` или новый `sb_secret_*` хранятся только в Edge secrets. Даже
сервисный RPC кэша дополнительно проверяет auth.role(). Нет эндпоинта, который
выдаёт эти ключи. В коде нет подключения к БД под postgres от Android или Edge.
Миграционная роль является владельцем объектов, а не ролью приложения.

## RLS и функции

Все 14 таблиц `lastpay` имеют ENABLE и FORCE RLS. Для каталожных данных есть
только SELECT-политики. Прямой DML, TRUNCATE и доступ к provider_cache клиентам
не предоставлены. Представление сохранений использует `security_invoker=true`.
Служебные таблицы закрытой схемы также имеют RLS; для реестра, окон и аренды
пользовательских политик нет. Справочник ISO доступен только для чтения.

Все функции имеют фиксированный пустой search_path и квалифицированные обращения
к схемам. EXECUTE FROM PUBLIC отозван для всех функций обеих схем. Права
возвращены по явному списку. Внутренний publish не предоставлен authenticated.
Параметры SQL связываются, имена таблиц берутся только из whitelist.

Границы SECURITY DEFINER:
- `is_admin`: читает только закрытый реестр текущего uid.
- `take_limit`: меняет только ограниченные окна заданного scope для текущего uid.
- `admin_rpc`: проверяет постоянную сессию и реестр до мутации; пишет атомарно.
- `save_rpc`: выбирает владельца только из auth.uid(), блокирует его слот, сверяет ревизию.
- `provider_rpc`: сервисный доступ только к кэшу, арендам и квотам, без произвольного SQL/URL.

Остальные функции SECURITY INVOKER. Триггеры запрещают изменение опубликованных
строк даже владельцу таблицы и блокируют родительскую версию FOR SHARE. Публикация
и административная запись держат FOR UPDATE одной версии, что предотвращает гонки.

Внутренняя ошибка SQL превращается в общий INTERNALERROR, SQL-текст не выдаётся.
Ожидаемые ошибки возвращаются из под-транзакции с откатом мутации. Счётчик лимита
увеличивается до этой под-транзакции, поэтому невалидные запросы тоже учитываются.

## Edge

`verify_jwt=false` отключает только устаревшую gateway-проверку. Handler сам
обязательно обращается к Auth `/user` с Bearer JWT и публичным ключом, проверяет
успех и постоянный uid. Не производится доверенное декодирование неподписанного JWT.
Проверка поддерживает современный publishable key в apikey и JWT в Authorization.
Ошибки Auth не дают обратиться к провайдеру или сервисному RPC.

Не логируются JWT, внешние URL с токеном CarsBase, содержимое ответов и секреты.
Полный Newman JSON намеренно не экспортируется. В CI публикуется allowlist отчётов.
Значения внешних ключей не являются частью Postman-коллекции или тестового отчёта.

## Ограничения и проверка на настоящем проекте

Локальный issuer Auth и проверка HS256 в tests/local_server.ts — только тестовая
фикстура; она не развёртывается. Она позволяет проверить подпись, срок действия,
двух владельцев и Edge без Docker. Реальные Auth входы двух подтверждённых пользователей, JWT-проверка Edge и platform
gateway проверены в облаке; см. evidence. Регистрация с доставкой письма, refresh и
Android end-to-end в объём выполненных проверок не входили. Кэширование /user локально отсутствует; в облаке эта проверка
занимает один дополнительный запрос Auth на вызов интеграции.

Защита на уровне функции начинается после invocation: запросы злоумышленника
могут расходовать квоту Edge даже при ответе 401. Для небольшого учебного проекта
контролируйте Usage, оставьте внешние ключи пустыми до проверки и ограничьте
распространение тестового приложения. Это не требует платного сервера.

Не открывайте lastpay_private в Exposed schemas. Не выдавайте клиентам прямую
запись в lastpay и EXECUTE на новые функции без ревью. Не отключайте подтверждение
почты или RLS только для упрощения тестов.
