# Диагностика DELETE и новой миграции 004

Статус: миграция 004 применена владельцем через CLI; последующая разрешённая
облачная регрессия прошла 28/28. До отдельного разрешения облачные DELETE
при диагностике не повторялись. Тестовая публикация не выполнялась.

## Установленные факты

В облаке запущен PostgREST 14.18 (лог запуска 2026-11-06 18:23:26 UTC).
В логе запроса DELETE в 19:19:29.272 UTC итоговый статус 412 и
`response.headers.x_envoy_attempt_count = 2`. У соседних запросов значение 1.
В pg_stat_statements — 6 выполнений delete_skill при 5 вызовах в сохранённых
сценариях (два запрета обычным пользователям ранее и три вызова CRUD-сценария).
SQL-аудит: тестовый навык отсутствует, тестовый черновик DRAFT/revision=4;
demo-1, активная версия и тестовые сохранения не изменены.

Исходный mutate выполняет DELETE, увеличивает ревизию, задаёт response.status=204
и возвращает SQL NULL. admin_rpc ловит LP412 и возвращает JSON ошибки; обёртка
delete_skill имеет RETURNS jsonb. Все три функции VOLATILE.

На реальных локальных PostgREST 14.18, 13.0.7 и 16.5 воспроизведён ответ:

```http
HTTP/1.1 204 No Content
Content-Length: 4
Content-Type: application/json; charset=utf-8
ETag: "rev-3"
```

Клиент не читает тело статуса 204. Четыре байта — сериализация JSON `null`;
Content-Length сформирован до применения response.status. Обычная проверка
только кода 204 ошибочно считала этот ответ корректным.

[PostgREST Response.hs 14.18](https://github.com/PostgREST/postgrest/blob/v14.18/src/PostgREST/Response.hs)
формирует длину тела JSON RPC до overrideStatusHeaders. Для RETURNS void
предусмотрен отдельный путь, но текущая функция RETURNS jsonb.
[RFC 9110 §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6)
запрещает Content-Length в ответе 204.
[HTTP/1 codec Envoy](https://github.com/envoyproxy/envoy/blob/main/source/common/http/http1/codec_impl.cc)
отклоняет ненулевой Content-Length для 204 с content_length_not_allowed.

Согласованная с этими свидетельствами цепочка: первая upstream-попытка
фиксирует удаление, некорректное HTTP-оформление вызывает отказ шлюза и повтор;
вторая транзакция видит увеличенную ревизию и возвращает LP412. Её откат не
может отменить первую уже завершённую транзакцию. Низкоуровневый журнал Envoy
с причиной первого reset недоступен; конкретный reset-code в облаке не наблюдался.
Повтор upstream подтверждён непосредственно облачным счётчиком попыток.

## Минимальное исправление

Новая миграция `202611060004_delete_response.sql` заменяет только две функции.
Обёртка DELETE вызывает admin_rpc один раз и преобразует его успешный NULL/204
в HTTP 200 с `{deleted:true,id,catalogVersion}`. Ошибки передаются без изменения.
Обновление данных, проверка ревизии, блокировки и вложенная транзакция остаются
в прежнем mutate/admin_rpc. Сигнатура, OID, владелец и ACL сохраняются.
Миграция не содержит DML, RLS, GRANT, DROP или изменения пользователей.

Это осознанное изменение успешного HTTP-контракта Supabase RPC с 204 на 200.
Старый Ktor OpenAPI остаётся историческим контрактом. Supabase Postman,
генератор, локальные проверки и RPC-документация обновлены. Клиент должен
принимать 200/receipt. Изменение RETURNS jsonb на void потребовало бы
пересоздания функции и другого способа передачи JSON ошибок; подмена длины
на 0 сохранила бы запрещённый RFC заголовок для 204.

Создание/изменение/публикация/сохранение возвращают непустой JSON со статусами
201/200. Для них этот конкретный дефект 204 отсутствует. Регрессия сопоставляет
ответы с SQL-состоянием и проверяет неизменность всех прикладных таблиц при
ошибках 400/401/403/404/409/412/500, включая искусственное исключение после DML.

Корректное HTTP-оформление устраняет найденный повод повтора; оно не даёт
гарантии exactly-once при произвольной потере ответа в сети. Автоматически
повторять мутации после неоднозначной транспортной ошибки нельзя. Для общей
защиты от повторной доставки нужен отдельный контракт idempotency key/receipt;
в эту минимальную миграцию он не включён.

## Сжатие и ETag

Ранее наблюдались W/"rev-1" при сжатии и сильные "rev-N" при identity.
Это отдельная проблема, не причина разобранного DELETE: проблемный запрос
использовал identity и сильный ifMatch, а ошибка пришла после повтора upstream.
[Cloudflare документирует ослабление ETag при изменении кодировки](https://developers.cloudflare.com/cache/reference/etag-headers/).
Миграция добавляет в etag() `Cache-Control: private, no-store, no-transform`.
[Cloudflare поддерживает no-transform для запрета сжатия](https://developers.cloudflare.com/speed/optimization/content/compression/).
Локальная проверка подтверждает сильный ETag и директиву для identity и gzip/br;
реальное поведение CDN после миграции ещё требует разрешённой HTTPS-проверки.
PostgREST локально не сжимает эти ответы, поэтому это не тест реального CDN.

Проверка ревизии читает `args.ifMatch`, а не HTTP-заголовок If-Match. Она по-прежнему
требует сильную строку "rev-N". W/ не удаляется и не принимается автоматически:
при слабом валидаторе клиент должен повторить чтение без преобразования ответа.

## Регрессия и оставшиеся действия

`server/supabase/scripts/test-mutation-responses.py --disposable-postgres` запускает
реальный PostgREST на 127.0.0.1 и новую случайную БД. Исходная ошибка проверяется
до миграции 004. Повтор шлюза моделируется явно по правилу Envoy; сам Envoy
локально не запускается. После миграции проверяются framing, receipt, ETag,
SQL-состояние, ACL, конфликты и откаты. Отчёт без токенов —
`server/supabase/.local/mutation-response-results.json`.

Фактические результаты 2026-11-06: регрессия на PostgREST 14.18 и 16.5 — по 99/99,
полный локальный набор на 14.18 — 53 Deno-теста, 342 SQL/API-проверки и
144 Newman assertions (48 запросов), без ошибок. Локальный Auth — JWT-фикстура;
это не повторная проверка реального Supabase Auth. Все записи и публикации этих
тестов происходили только в случайных одноразовых локальных БД.

Облачная регрессия после отдельного разрешения: новый черновик
delete-fix-20261106-56fa9eba от demo-1; создание навыка 201/rev-2; удаление
200/receipt/rev-3; чтение удалённого навыка 404; stale DELETE 412 без изменения
SQL digest/revision. Успешный DELETE имеет x_envoy_attempt_count=1 в заголовке
и в историческом облачном логе по request_id. При identity и gzip/deflate/br
ETag сильный, Content-Encoding отсутствует, Cache-Control содержит no-transform.
demo-1 и сохранения игроков неизменны; черновик остался DRAFT. Дефект устранён
в проверенном сценарии. [Фактический отчёт](evidence/cloud-delete.json).
Общая гарантия exactly-once при произвольной потере ответа по-прежнему требует
отдельной идемпотентности. Положительная публикация требует нового разрешения.
